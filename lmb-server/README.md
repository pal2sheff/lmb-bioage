# lmb-server 0.5.0

Серверная часть LMB BioAge: очередь 0 и задачи 1.1 ТЗ v1.0. Расчёты выполняет пакет `lmb-engine`, который лежит рядом в соседней папке.

## Что реализовано

- **База данных.** PostgreSQL 16, миграции Alembic. В базе: клиники, пользователи, роли, сеансы, пациенты, визиты, справочник показателей, наблюдения с редакциями, анкета, версии модели, снимки входов, расчёты, журнал аудита.
- **Изоляция клиник** в два слоя:
  - фильтры в коде; чужая карточка возвращает 404;
  - политики строк PostgreSQL (RLS). Роль приложения `lmb_app` не может обойти политики и не может удалять медицинские записи. Журнал аудита для неё доступен только на добавление.
- **Вход:**
  - пароль хранится как хеш Argon2id, минимальная длина — 12 символов;
  - сеанс — в cookie HttpOnly, SameSite=Strict;
  - на каждое изменение данных требуется CSRF-токен;
  - для персонала обязателен второй фактор TOTP: без него доступны только вход и его подключение.
- **Роли по матрице ТЗ 2.2:**
  - врач — клинические данные и расчёты;
  - администратор клиники — пользователи и идентификация пациента, без клинических данных; полномочие ответственного за модель администратор выдать не может;
  - исследователь и пациент — без доступа к карточкам.
- **Карточка пациента:**
  - ФИО, ИИН, телефон и e-mail зашифрованы (Fernet, ключ `LMB_FIELD_KEY`);
  - поиск по ИИН и по полной фамилии — через слепые индексы (HMAC, ключ `LMB_INDEX_KEY`); фамилия сравнивается без учёта регистра и «ё/е», поиск по началу фамилии невозможен; список без запроса — 50 последних карточек, по алфавиту после расшифровки;
  - изменение карточки — с проверкой версии (If-Match) и указанием причины.
- **Наблюдения.** Исправление создаёт новую редакцию, прежняя сохраняется. Без причины исправление не принимается, в том числе ограничением базы. Импорт ждёт подтверждения врача. Значения «<» и «>» и отсутствие числа (null) хранятся как есть.
- **Анкета.** Отсутствующий ответ — «неизвестно», а не «нет». Каждый новый ответ сохраняется отдельной редакцией.
- **Расчёт:**
  - неизменяемый снимок входов с SHA-256, одинаковые входы дают один снимок;
  - результат lmb_engine сохраняется вместе с версиями модуля, модели и конфигурации;
  - операция `reproduce` подтверждает, что результат воспроизводится;
  - повтор запроса с тем же Idempotency-Key не создаёт дубликатов.
- **Модель v0.3** хранится в базе редакциями: строка версии неизменяема, изменение конфигурации — новая редакция, прежняя переводится в архив и остаётся для воспроизведения старых расчётов. Редакция 1 — только веса; редакция 2 (миграция 0005) — нормализация 12 показателей и правила семи доменов из пакета владельца от 11.10.2026. Обе: использование не разрешено, научно не проверены. Расчёт берёт последнюю неархивную редакцию и сохраняет ссылку на неё.
- **Анкета для CAIDE:** физическая активность по определению шкалы («неизвестно» ≠ «неактивен») и полные годы обучения (целое 0–30 или «неизвестно»).
- **FRAX (ТЗ 10.1):**
  - запрос собирается из снимка визита и содержит только расчётные признаки: возраст, пол, ИМТ, семь факторов риска и МПК шейки бедра; ФИО, ИИН, дата рождения и идентификаторы не передаются;
  - возраст вне 40–90 лет — запрос не отправляется, граница не подставляется;
  - «неизвестно» блокирует запрос; отметка врача «нет — сведений нет, по правилу FRAX» выключена настройкой до решения владельца;
  - МПК — только шейка бедра: T-показатель либо г/см² с производителем денситометра;
  - провайдеры: «не настроен», облачный FRAXplus, локальный Docker-экземпляр FRAXplus, ручной ввод врача;
  - повтор с теми же входами не расходует лимит; при использовании 90 % годового лимита выводится предупреждение;
  - тайм-аут 15 с, до 3 попыток с паузами 2 и 8 с; учитывается Retry-After; ошибки авторизации и запроса не повторяются;
  - ответ HTTP 200 принимается, только если оба риска — числа от 0 до 100, горизонт 10 лет, модель Kazakhstan и признак МПК совпадает с запросом;
  - результат привязан к хешу входов: поздний ответ после изменения данных сохраняется, но в новый расчёт не попадает;
  - автоматический результат не заменяет ручной незаметно: при двух результатах для одних входов действующий выбирает врач;
  - ручной ввод официального результата работает независимо от анкеты. Если факторы риска внесены полностью, результат привязан к ним и устаревает при их изменении. Если нет — он действует для визита с пометкой «анкета неполная», а в расчёте Bone появляется предупреждение. Проверки те же: возраст 40–90 лет, оба риска 0–100 %, дата расчёта не в будущем, модель Kazakhstan. К результату можно приложить файл официального расчёта;
  - тестовый провайдер запрещён вне тестовой среды, в том числе ограничением базы;
  - очередь обрабатывает `python3 -m lmb_server.frax.worker`.

## Файлы (вложения)

- Файлы хранятся **только на диске сервера клиники** в каталоге `LMB_FILES_DIR`. В облачные хранилища и сторонние сервисы они не передаются.
- Каждый файл зашифрован ключом `LMB_FILES_KEY` (Fernet: AES-128-CBC + HMAC-SHA256). Без ключа содержимое не читается. Права: файлы 0600, каталоги 0700.
- Допустимы PDF, PNG и JPEG. Тип определяется по содержимому, а не по имени файла. Предельный размер — `LMB_MAX_UPLOAD_MB` (по умолчанию 20 МБ).
- Имя файла хранится в базе зашифрованным. В журнал аудита записываются загрузка и каждое скачивание, без имени и содержимого файла.
- При скачивании проверяется контрольная сумма SHA-256: подменённый на диске файл не выдаётся.
- Изменять и удалять записи о файлах роль приложения не может. Ключ `LMB_FILES_KEY` и резервные копии каталога файлов хранятся раздельно.
- Операции: `POST /encounters/{id}/attachments` (multipart: `kind`, `file`), `GET /encounters/{id}/attachments`, `GET /attachments/{id}`.

## Что нужно для автоматического FRAX

Код отправки готов, но сопоставление полей FRAXplus API намеренно не заполнено (`frax/providers.py`, класс `Mapping`). Спецификация API на 10.10.2026 не загрузилась: страница формируется скриптом. Пока сопоставления нет, провайдер возвращает «интеграция не настроена» и запрос не отправляет. Подтверждено документацией:

- локальный Docker-образ принимает ключ в заголовке `x-api-key`;
- в CSV-спецификации пол кодируется так: 0 — мужчины, 1 — женщины.

Для включения нужны:

1. Лицензия FRAXplus.
2. Действующая спецификация API.
3. Новый класс `Mapping` с подтверждёнными полями и кодом Казахстана из справочника стран.
4. Реальные запросы с синтетическими случаями (раздел 18.2 ТЗ).

Настройки: `LMB_FRAX_PROVIDER`, `LMB_FRAX_BASE_URL`, `LMB_FRAX_API_KEY`, `LMB_FRAX_MAPPING`, `LMB_FRAX_ANNUAL_LIMIT`, `LMB_FRAX_ALLOW_ASSUMED_NO`, `LMB_FRAX_STORE_RAW`.

## Отклонение от ТЗ

В ТЗ для документов указано отдельное объектное хранилище (S3-совместимое). По решению владельца от 10.10.2026 файлы хранятся на локальном диске сервера клиники в зашифрованном виде (раздел «Файлы»).

ФИО шифруется с 11.10.2026 (миграция 0006 переносит существующие карточки; для неё нужны те же ключи, что и серверу). Если ключ `LMB_FIELD_KEY` потерян, ФИО, ИИН и контакты восстановить нельзя: ключ хранится и резервируется отдельно от базы.

## Развёртывание

1. Подготовьте базу и роли:
   ```bash
   psql -v admin_password=… -v app_password=… -f deploy/init_roles.sql
   ```
2. Задайте переменные окружения:
   - `LMB_DATABASE_URL` — подключение роли `lmb_app`;
   - `LMB_ADMIN_DATABASE_URL` — подключение роли `lmb_admin`;
   - `LMB_FIELD_KEY` — ключ Fernet;
   - `LMB_INDEX_KEY` — 32 байта в base64;
   - `LMB_FILES_DIR` — каталог файлов на диске сервера;
   - `LMB_FILES_KEY` — отдельный ключ Fernet для файлов;
   - `LMB_MAX_UPLOAD_MB` — предельный размер файла, по умолчанию 20.

   Ключи хранятся только в хранилище секретов.
3. Примените миграции и создайте клинику с первым администратором:
   ```bash
   alembic upgrade head
   LMB_BOOTSTRAP_PASSWORD=… python3 -m lmb_server.bootstrap --clinic "Love my body" --email … --name …
   ```
4. Запустите сервер:
   ```bash
   uvicorn lmb_server.main:app
   ```
   В рабочем окружении сервер ставится за обратный прокси с TLS. Спецификация API: `/api/v1/openapi.json`.

## Тесты

```bash
pip install -e ".[test]"
python3 -m pytest --cov=lmb_server --cov-branch
```

Тесты сами поднимают временный кластер PostgreSQL 16 без Docker и применяют миграции. Затем они создают две клиники с пользователями всех ролей. Тест `alembic check` проверяет, что модели и миграции совпадают.
